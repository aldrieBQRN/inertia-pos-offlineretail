# Cashier POS Terminal — Test Cases

Automated end-to-end test cases for the Cashier POS Terminal (`/pos`, `resources/js/Pages/PosTerminal.jsx`).
Every case below is backed by a Playwright test in `e2e/02_cashier_pos/` and describes what the test actually does.

| | |
|---|---|
| **Framework** | Playwright (`@playwright/test`), Chromium "Desktop Chrome" project (1280×720) |
| **Run command** | `npm run test:e2e:cashier` (= `npx playwright test e2e/02_cashier_pos`) |
| **Prerequisite** | Laravel app served at `http://127.0.0.1:8000` (`php artisan serve`), seeded database |
| **Login** | `cashier@email.com` / `password` (`e2e/fixtures/test-data.js`), via `loginAsCashier()` |
| **Shared helpers** | `e2e/fixtures/pos.helpers.js` (selectors, in-page API calls, cart/checkout/shift helpers) |
| **Last result** | 2026-10-03, after moving Cash In/Out to the Manager/Admin Shift page: cashier suite **29 test cases: 28 passed, 0 failed, 1 blocked/manual**. Manager/Admin Shift suite (`e2e/05_admin_shifts`) 5 passed. Full E2E suite 71 passed, 1 skipped (the blocked printer test). |

## How the tests get their data

- **No hardcoded products or totals.** Each test reads the live catalog (`GET /api/products?all=true&active=true`) and picks active, in-stock products (highest stock first). It then computes expected prices, line totals, subtotals, discounts, change and drawer balances from those values.
- **Shift state is set up via the app's own API.** Setup steps call `window.axios` inside the page, so CSRF is handled: they close an active shift as balanced or open a fresh one. The Open Shift and Close Shift features themselves are always tested through the UI.
- **Results are checked twice.** Once in the UI, and once against what was persisted: `GET /api/transactions/{id}`, `GET /api/shift/current`, `GET /api/held-orders`, and the `/api/shift/close` response.
- **Side effects (local dev database):** each full run completes about 17 sales (stock goes down), creates and closes about 6 shifts, and records two cash movements as the Manager/Admin (POS-028). Saved orders created by the tests are deleted or recalled by the same test.
- Amounts are shown as the UI renders them (en-US grouping, 2 decimals). The ₱ sign appears only where the UI prints it: payment success dialog and discount preview.

## Responsibility split: Cash In/Out

> Cash In/Out is intentionally not available in the Cashier Terminal. Cash movements are handled by the Manager/Admin through the Shift page.

The Cashier Terminal has no Cash In/Out button and no F4 shortcut for it; POS-025 guards this. The cashier still sees the effect of a manager's cash movement on their shift in the header **Drawer** value (POS-028). Cash In/Out itself is tested in the Manager/Admin suite (see [Related Manager/Admin tests](#related-manageradmin-tests)).

## Related Manager/Admin tests

Cash In/Out moved out of the cashier suite and is covered on the Manager/Admin Shift page (`/shifts`) in `e2e/05_admin_shifts/02_cash_movements.spec.js` (run with `npx playwright test e2e/05_admin_shifts`). The file opens a dedicated cashier shift and closes it again (balanced) when done.

| Test | What it verifies |
|---|---|
| `2.1 should record a Cash In from the Shift page` | Admin opens **Cash In / Out**, targets the cashier's active shift and records a Cash In / Deposit. The movement (201, `cash_in`) is saved on the shift, and the drawer shown for that shift rises by the amount. |
| `2.2 should record a Cash Out from the Shift page` | Same for a Cash Out / Expense (`cash_out`); the drawer falls by the amount. |
| `2.3 should block a Cash Out above the drawer balance` | A Cash Out of drawer + 0.01 shows "Insufficient Drawer Funds" with the exact message, and **Insufficient Drawer Balance** is disabled. No request is sent and the drawer is unchanged. |

## Application issues found during automation

These defects were found while automating the suite. All three were **fixed on 2026-10-03**. Each was reproduced in the browser before the fix and confirmed fixed afterwards; the full cashier suite still passes.

| # | Area | Issue (before fix) | Fix | Where | Status |
|---|---|---|---|---|---|
| 1 | Cash In/Out | *(Found while Cash In/Out was still in the Cashier Terminal; that entry point has since been removed. The fix remains in the shared modal used by the Manager/Admin Shift page.)* The modal's reset effect depended on `shiftData`. After a checkout or a cash movement the POS refreshes shift data twice (`onMovementRecorded` / `onCheckoutSuccess` plus the `shift-refresh` event). If a refresh landed while the modal was open, the typed **amount and reason were cleared**. | The form reset and target loading now run only when the modal opens (`[isOpen, user?.is_admin]`). A separate effect keeps the displayed drawer balance in sync with `shiftData` without touching the inputs. | `resources/js/Components/CashMovementModal.jsx` | Fixed |
| 2 | Recall Saved Orders | Opening the modal starts `GET /api/held-orders`. If an order was discarded or recalled before that request returned, the late response **put the removed order back in the list**, even though the server had already deleted it. | Each list request carries a version number (`heldOrdersVersionRef`), and discard/recall bump it. A response is applied only if no newer request or local change happened after it was sent, so stale responses are ignored. Refreshing the list still works. | `resources/js/Pages/PosTerminal.jsx` | Fixed |
| 3 | Cash movements (admin path) | `ShiftController::cashMovement` called `Terminal::find(...)` without importing `App\Models\Terminal`. An admin deduction aimed at a register between shifts returned HTTP 500 (`Class "App\Http\Controllers\Api\Terminal" not found`). | Added `use App\Models\Terminal;`. The same request now runs the drawer-balance check (e.g. 422 "Insufficient cash in &lt;register&gt; Drawer" when over the limit). | `app/Http/Controllers/Api/ShiftController.php` | Fixed |

The suite still waits for the Recall list refresh (issue 2), because it waits for real UI state. The shift-refresh wait used for issue 1 was removed along with the cashier Cash In/Out tests.

Other observed behaviour (not a defect): entering a quantity above stock is blocked by the browser's own validation (`max` on the quantity input). So the app's custom "Limit Reached" toast in `handleConfirmQty` does not appear from the modal form; the excess quantity is still prevented.
